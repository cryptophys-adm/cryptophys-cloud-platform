## Platform rules

These hold everywhere:

- **No fund movement; trading only with the owner's click.** Wallets, withdrawals, transfers and other fund movements are prohibited at every tier. Since 2026-11-12 (owner: "larangan trading harus dicabut karena kita sudah masuk fase production", "Trading boleh, dana tidak"; ADR-0009 amendment), a trading action is allowed but always critical (consensus, then one owner click), and a trading capability must be tier 2 or above. Nothing in the platform trades yet. The knowledge validator's rules for learned knowledge (no orders, no price levels) are unchanged.
- **No containers.** Production runs on Workers and their bindings only (ADR-0005 decision 1). The Forge type-check, which does not fit in an isolate, runs on Workers Builds from the Artifacts repository (ADR-0012 §5c, owner 2026-11-08; first report passed 2026-11-09).
- **Never weaken Access, auth or tests.** No test is skipped. A test that cannot run somewhere keeps running where it can.
- **The owner creates every secret and credential.** None is created by an agent or stored in the repository.
- **Data deletion and irreversible actions are critical.** The owner decides them.
- **The brake always works.** Consensus mode `shadow` and the kill switch (`kernel_controls.agents_enabled`) can be used at any time.
- **Repositories out of scope.** `cryptophys-adm/xauusd-ai-trading-assistant` (Nexus) and `cryptophys-adm/cryptophys-aether` are not changed from this repository. Since 2026-11-14 (owner; ADR-0016), agents may change Aether in its own repository only after its bootstrap PR (DNA, CI DNA tests, guard paths) is merged, and then only through its CI, with its guard paths needing the owner's click. Until then Aether is read-only for agents.

## Entry point and sign-in (ADR-0008, ADR-0010, ADR-0011)

- **Hosts.** `https://nexus.cryptophys.work` is the only public origin. The Cerebrum Console is mounted at `/console/`, through the Workers route `nexus.cryptophys.work/console*`. The old hostnames `console.cryptophys.work` and `home.cryptophys.work` are retired (owner 2026-11-13, ADR-0010 amendment): one `retire-worker.yml` run detaches both custom domains (then they no longer resolve) and deletes `cryptophys-home`. Until that run, `console.` still redirects to the mount (`LEGACY_HOSTS`).
- **Sign-in.** Cloudflare Access is the only login. The identity providers are Google, Microsoft (OIDC) and one-time PIN (kept for now by owner decision, 2026-11-08). There is one Access application, `cryptophys-cloud-platform`, so there is one AUD and one 8-hour session.
- **Roles.** Configured identities come from `OPERATOR_IDENTITIES` and `APPROVER_IDENTITIES` (the owners). Accounts live in D1 `platform_accounts`:
  - `admin`: viewer, operator or approver;
  - `user`: Nexus only.

  Every Worker checks roles itself through `control-plane-shared/src/access.ts`.
- **Writes that shape production** (a recovery plan by hand, a service record, a desired version) need the approver role for a person (`requireApproverOrServiceOperator`, 2026-11-08). The deploy workflows' service token keeps recording versions and its verification plan, which is marked `synthetic` and hidden from the Console list.
  - Since 2026-11-15 (owner: "tombol Edit tidak berfungsi") the Console no longer edits a service record or a desired version: the Infrastructure page's Edit form and the routes `registry.upsert` and `registry.desired_version` are gone, and the Console refuses both registry `PUT`s (404). Registry records come from the DNA, the census, migrations and consensus deploys; a manual edit conflicted with the DNA and created false drift.

  - Sign out goes to `/cdn-cgi/access/logout`.
  - Switch account goes to `/console/switch-account`.
  - A Nexus-only account that opens the Console gets the access page.

## Data

- **D1 `cryptophys-control-plane`.** One database for every service. Migrations live in `workers/control-plane-migrations/`, numbered from 0001; each Worker's readiness lists the ones it needs.
  - Migrations are applied **only by the Control Plane deploy**, so a commit with a new migration deploys the Control Plane first. "New" is read from D1: a file of main's migrations directory that `d1_migrations` does not list (the Forge's deploy plan, 2026-11-14).
  - Every service requires `REQUIRED_MIGRATIONS` (`control-plane-shared/src/readiness.ts`). The Forge also requires 0031–0033 and 0035.
- **Drift observations on change (owner, resource audit decision 1, 2026-11-14, migration 0061).** The Drift Detector records a `drift_observations` row only when a service's state changes (drifted, desired and observed hash, sorted reasons); the same state on a later run raises the row's `streak` to 2 once. Persistent drift is "the newest row drifted and its streak is 2 or the row before it drifted" (`control-plane-shared/src/drift-state.ts`). `service_registry.updated_at`, set by every run for every service but a retired one (0064), is the heartbeat: staleness, verification freshness and the Console's "last probe" use it (`GET /v1/drift` returns it as `last_seen_at`; a registry write such as a deploy's desired version also sets it). A row's `observed_at` is when its state was first seen, not the last probe. `drift.observation` is audited only for a run that changed a state or published a report.
- **Untagged versions.** A dashboard secret or variable change creates an untagged Worker version, so the Drift Detector cannot read the running version: the service reads as `observed_version_unavailable` (drifted) until the next deploy records a tagged version. It is not a recovery case (`onlyUntaggedVersion`, ai-kernel `supervisor.ts`); the Console's Infrastructure page shows it as "untagged version (dashboard change)", not as "drifted" (`control-plane-shared/src/service-detail.ts`).
- **Console Infrastructure page (owner 2026-11-15).** Read only, with "Observe now". A click on a service opens its detail (a bottom sheet on a phone, a side panel on a desktop) from GET routes only: Observer vitals and findings (`GET /v1/observer`: error rate, CPU p99 and requests over the hours it serves; D1 rows per request is not attributed to a Worker, so only the labelled account-wide estimate is shown), the latest deploy request and recorded version (`GET /v1/deployments`), the organ's DNA (`GET /v1/forge/census`), and its drift state, reasons and recorded changes (`GET /v1/drift`, `GET /v1/drift/{id}`). A missing value reads "not measured".
- **Retention.** `observer_vitals` and `observer_runs` keep 30 days and `observer_findings` 90 days (migration 0063, swept in code at 03:27 UTC). `drift_observations` keeps 90 days and `agent_syscall_consumptions` 7 days (owner, 2026-11-05). `forge_builds` keeps 100 days and `forge_build_collections` 30 days (the Workers Builds API itself keeps 90). `forge_dependency_audits` and `forge_dependency_findings` (G5, migration 0051) keep 90 days. `forge_git_backups` (gate 8, migration 0054) keeps 90 days, except rows whose bundle is still in R2. Other tables are kept.
- **Forge bundles (G2a, 2026-11-12).** The R2 bucket `cryptophys-forge-bundles` holds the Worker modules and a manifest of every passed main commit, for 14 days (`workers/forge/src/bundles.ts`).
- **Backups.** The R2 bucket `cryptophys-d1-backups` gets a daily backup written by the Recovery Manager, with a 90-day lifecycle. D1 Time Travel is also available. A restore is critical (owner).
- **Repository backup (ADR-0012 gate 8, §5m, 2026-11-13).** Once per UTC day per head of main, the Forge clones `cryptophys/platform` over Git smart HTTP. It writes the result as a git bundle to `cryptophys-forge-bundles` at `git-backups/platform/<UTC date>-<main sha>.bundle`, with its SHA-256 in D1 and in the object's metadata. It keeps the newest bundle of each of the last 30 days (`GIT_BACKUP_RETAINED_DAYS`).
  - `GET /v1/forge/git-backup` and the Console Code page show the backups. A backup that has not succeeded for 48 hours is shown on the Console only, never sent as an owner notice.
  - Restore: `git bundle verify <file>`, then `git clone <file> platform-restore`. A restore is critical (owner).

## The living platform (ADR-0013)

- **DNA.** Every Worker declares itself in `workers/<dir>/organism.json`: service, deploy unit, Access, rollback, drift probe, hosted agents (voter or not), AI engines. CI fails when a static list (deploy units, drift probes, Access, rollback, council, kernel agents, vote bindings, engines, names) disagrees with the DNA.
- **Census (phase 2).** The Forge compares the DNA of each main commit with `service_registry`, `agents` (and their seats) and `engines` (`forge_organism_census`, retaken every 30 min). Differences become the owner notice `organism` and appear on the Console Agents page. Findings the Supervisor registers by itself (an unregistered engine or agent) send one email when they appear and one when all are registered, not one per registration (owner 2026-11-12).
- **Self-registration (phase 3).** The Supervisor turns census findings into consensus proposals, one per cycle:
  - `register_agent` and `register_engine` are routine: consensus only.
  - `retire_engine` (owner 2026-11-15) is routine too, the mirror of `register_engine`: an enabled engine whose organ's DNA no longer declares the task (`undeclared_engine`) is proposed once the finding stood in 2 consecutive census rows or for 1 h, never for an organ whose origin's DNA was not read (`external_dna_unavailable`), with `register_engine`'s cooldown and hourly limit per Worker, after any registration waiting. The kernel sets `engines.status = 'retired'` (audit `engine.retired`); nothing is deleted and `ai_usage` keeps its history. A DNA that declares the task again re-enables the row through `register_engine`.
  - `register_privileged_agent` (a capability above tier 1, or `consensus.propose`) and `admit_voter` (a council seat, one per Worker) are critical: consensus plus the owner's click, in mode `deploy` or `critical` (owner 2026-11-13).
  - The kernel takes the gene from the census, never from the proposal, so only merged DNA can register. Tier 3, unknown and fund-movement capabilities are never registered; a trading capability registers only as privileged (the owner's click).
  - A new seat must vote through a reviewed vote binding; without one it is refused. A seat the DNA no longer asks for is reported, never removed by an agent.

## The Observer (owner 2026-11-14: "setuju"; "gak perlu shadow, langsung production")

- **Where.** `cryptophys-platform-api`, cron `27,57 * * * *`, with the read-only `CF_ANALYTICS_TOKEN` (or `CF_BILLING_TOKEN`) and `CF_ACCOUNT_ID` it already holds for `GET /v1/usage`. Code: `control-plane-shared/src/observer.ts` and `observer-inventory.ts`; the Supervisor's side is `ai-kernel/src/observer-watch.ts`.
- **Senses (hourly, :27, the last complete UTC hour).** Six GraphQL Analytics calls, one per dataset, for every Worker on the account (platform, XAUUSD, Aether): `workersInvocationsAdaptive` (requests, errors, CPU and wall time p50/p99, exceededCpu / exceededMemory / exception counts by status), `d1AnalyticsAdaptiveGroups` and `d1QueriesAdaptiveGroups` (rows read and written, queries, the top queries by rows read), `kvOperationsAdaptiveGroups`, `durableObjectsInvocationsAdaptiveGroups`, `aiInferenceAdaptiveGroups` (neurons by model). A dataset that fails or is empty is recorded as such and adds nothing. Top error messages come from the Workers Observability telemetry query API; a token without `Account > Workers Observability > Read` is the finding `observability_permission_missing`, and the call waits 24 h.
- **Inventory (:27 and :57).** Live Workers (scripts list and the scripts seen by the analytics), D1, KV, R2, Queues and Durable Object namespaces against the union of all DNA in the Forge's latest census (including `EXT_ORGANISM_*`) and the resources this repository's wrangler files bind. Findings: `undeclared_worker`, `undeclared_resource` (informational until storage DNA exists), `orphaned_declaration`, `idle_worker` (7 days without traffic, only once the Observer has 7 days of senses). Preview and environment copies, Workers disabled in the registry and organs of an origin whose DNA was not read are never reported. A list the token may not read is a finding naming the permission. Bindings (owner 2026-11-15, "tambahkan"; `observer-bindings.ts`, migration 0068): each listed Worker's bindings are read from `GET /accounts/{id}/workers/scripts/{name}/settings` (Workers Scripts Read, at most 50 per run, failures per Worker) into `observer_worker_bindings`, one row per Worker, values never kept and part of the digest; `unbound_resource` (informational, only when every Worker was read), `binding_to_missing_resource` (warning), `bindings_unread`, `bindings_cap_exceeded`; `boundBy` and `GET /v1/observer` `inventory.bindings` answer whether any live Worker binds a resource and whether that answer is complete. A queue is referenced by Worker bindings, by its consumers (a Worker or an HTTP pull consumer) and by the `dead_letter_queue` setting of another queue's consumer, read from the queues list's `consumers` or, when the list does not carry them all, from `GET /accounts/{id}/queues/{queue_id}/consumers` (Queues Read, at most 50 per run); while any queue's consumers are unread no queue is `unbound_resource` and `queue_consumers_unread` (or a capability finding) names them (2026-11-15: `xauusd-webhook-events-dlq`, the dead-letter queue of `xauusd-webhook-events`, had been reported unbound). Pages project bindings are not read by the Observer, so "unbound" never covers what only Pages Functions bind. A resource named in an external organ's CI preview config (a `wrangler.preview.jsonc`, or the `previews` / `env.preview` block of a wrangler file) is `ci_preview` (informational, used intermittently by CI previews), never `unbound_resource`; the census reads external DNA over RPC, not repository files, so these are the reviewed list `CI_PREVIEW_RESOURCES` in `observer-inventory.ts`, each with its source (today the xauusd preview KV, D1 and queues).
- **External origins (`EXTERNAL_ORIGINS`, `control-plane-shared/src/organism.ts`, a guard path).** xauusd (`EXT_ORGANISM_XAUUSD`), Aether (`EXT_ORGANISM_AETHER`, its own per-agent ceiling) and, since 2026-11-15, `cryptophys-cta` (`EXT_ORGANISM_CTA`, schema `cta-organism.v1`, the general external ceiling; repository `cryptophys-adm/cryptophys-cta`). The Forge reads an origin only when its binding is bound; `EXT_ORGANISM_CTA` is bound once the Worker is live.
- **Storage.** One vitals row per Worker (and per D1 database, KV and DO namespace, AI model) and hour; findings only for anomalies, warnings, inventory differences and missing permissions, each `{worker, metric, value, baseline_7d, z, since_deploy, sample}`. `GET /v1/observer` (operator, read only) feeds the Console's Organism page.
- **Rollback (production, no shadow phase).** An error- or exception-rate spike of a platform Worker right after its most recent deploy becomes one `rollback_worker_version` proposal (to the previous recorded version) through normal consensus, only when: the Worker has at least 3 days and 24 usable hours of baseline; the hour has at least 200 requests and 20 errors (exceptions), a rate of at least 5 %, at least 3x the 7-day baseline and z >= 3; the hour overlaps the first 2 h after that deploy and the proposal is made within 3 h of it; no rollback of that Worker was proposed in the last 6 h; and no critical report is open. The consensus, every voter's brake, the Supervisor's rate window and the Policy Engine still decide. Trading Workers (`xauusd-ai-trading-assistant`, `xauusd-omega`, `xauusd-tradingview-pull-adapter`), Aether, the AI Kernel itself and Workers without a platform deploy unit are reported only. A commit rolled back this way is not proposed for deployment again by the deploy loop for 24 h.
- **Deploy stall alarm (owner 2026-11-14, after that day's incident: main moved with green Forge checks from about 15:00 UTC, the plan listed no unit (`forge_skipped`: control-plane `compare_failed_or_diverged`, `new_migration_control_plane_unavailable`), nothing deployed for over 6 h, and nobody was told).** At :27 and :57 the Observer checks, from D1 only (`control-plane-shared/src/deploy-stall.ts`): main's head (the Forge's newest plan) is `ready`; a deploy unit's Workers do not run it (`service_registry.desired_version`); the plan lists a unit or a skip (a plan with neither means nothing is due, and a disabled unit's skip is not a fault); and no `deploy_commit` has executed for more than 2 h, counted from the later of the last executed `deploy_commit` and the first plan with work for a newer commit.
  - **The report** is one `platform_digest` **warning** by agent `platform-api` per stall episode, in metric form (`deploy_stall_minutes` against 120): main's sha, the latest plan's `forge_skipped` and units, what the deploy loop sees, the last executed `deploy_commit` and its age, and the units behind with what they run. Its `alert_key` is `deploy_stall:<the last executed deploy_commit's proposal id>`, so a new main commit during the stall raises nothing new.
  - **Never critical, on purpose.** An open critical report is the consensus brake: every voter rejects every routine action, `deploy_commit` and `merge_change` included, until the owner acknowledges it. A critical stall alarm would block the deploy, and the merge of the fix, that end the stall. Exempting a kind from the brake would change `consensus-rules.ts` (a guard path) and weaken the brake, so the alarm is a warning, as every Observer report is.
  - **The owner** hears of it through the owner notice `production_unhandled` (code `deploys_stalled`, the Owner page and Telegram): one message when the episode's alarm opens and one when it ends, not one per run or per commit.
  - **Resolution.** Once a `deploy_commit` executes (the key changes), or when no unit is behind or nothing is due, the next Observer run publishes a `Resolved:` info report with the same `alert_key` and `state: "resolved"`, which the kernel's reports overview reads as resolved, and the notice closes. A head whose checks are still running does not close it.
- **Advisory only.** D1, KV, Durable Object and AI load spikes (naming the top D1 query) and CPU p99 at 80 % of the Worker's limit (30,000 ms on Workers Paid unless its wrangler `[limits]` say otherwise) are cycle findings and one `platform_digest` warning report per hour by agent `platform-api`, never critical.

## Trading organ health (Signal Analyst, owner 2026-11-15)

- **What changed.** The Signal Analyst (AI Kernel, :22 every hour, deterministic, no AI call) no longer relays each XAUUSD decision with its reasoning; Nexus and xauusd's own Telegram heartbeat do that. It reports the organ's health in metric form. All its reports stay kind `xauusd_digest` (no migration: the report kinds are a D1 constraint), and it never carries a price level.
- **Warnings, unchanged in kind and subject:** the source is unavailable (`XAUUSD decisions unavailable (…)`, at most every 6 h), the list is empty (`XAUUSD decisions empty`, at most every 6 h), the analysis is stale (`XAUUSD analysis stale: …`, once per candle). The BUY↔SELL flip is now a warning of its own, `XAUUSD H1 flip BUY -> SELL (confidence …) for candle …`, once per flipped candle, at most 2 per cycle (`reports.publish` allows 4 an hour); a flip that happened before the agent kept a window is not reported.
- **The snapshot.** One info report, `body.schema = "trading_organ_health.v1"`, whose `metrics` are `{metric, value, baseline_7d, z}`:
  - `decisions_24h`, the shares `share_buy_24h`, `share_sell_24h`, `share_wait_24h`, `share_no_trade_24h`, `flips_24h` and the confidence mean, p50, min and max, over the decisions of the latest decision's timeframe whose bar closed in the last 24 h;
  - `latest_decision_age_bars`: (now − the latest bar's close) / the bar length (H1: 60 min; M15 when the source serves the Decision Engine);
  - `staleness_incidents_24h` and `_7d`: a stale latest decision (once per candle) or the start of an empty list;
  - `hit_rate_7d` and `hit_rate_30d`: the `hit_rate` (hit / (hit + miss)) of the `7d` and `30d` windows of xauusd's `outcome_summary` (served with the decisions since xauusd 8a27029, scoring `cryptophys.outcome-scoring.v3`). `signals.observe` passes it through strictly validated (known fields only, counts and rates typed, everything else dropped, never a price field) and only for the subject of the endpoint it read: `engine:15` for `/api/engine/decisions`, `chain:h1` for the `/api/decisions` fallback. Each hit rate also carries `status`, `n_directional`, `hit`, `miss`, `wait_accuracy`, `subject` and `as_of` next to the four core fields. `status` is `ok` with a value; `no_scored_data` when the summary is there but nothing directional is scored yet (`n_directional` 0, `hit_rate` null: the market is closed, or the subject is new); `unavailable_source_field` when the summary or its window is absent, null (the scorecard read failed) or for another subject. Nothing is invented. Their baseline and z come from the same hourly samples as the other metrics.
- **History.** `signals.observe` returns the newest `limit` decisions (the agent asks for 50, the kernel's maximum) with no time window, so the agent keeps the last 48 h of decisions in its Durable Object storage (`xauusd_window`) and one sample per UTC hour for 7 days (`organ_health_samples`). `baseline_7d` is the mean of the earlier samples of the last 7 days and `z` is (value − mean) / standard deviation; with fewer than 24 samples both are `null`.
- **Publish rule.** The first snapshot; then only on a material change against the last one published (a value appears or disappears; `flips_24h` or a staleness count changes; `decisions_24h` moves by max(2, 10 %); a share, confidence statistic or hit rate moves by 0.05; a hit rate's status changes; a metric newly reaches |z| ≥ 3; the staleness flag changes), or at the 6 h heartbeat. An identical snapshot is not published every cycle; the age alone never publishes one.
- **Readers.** The overview (`GET /v1/overview`, `/v1/status`) carries `trading_organ_health`, the newest snapshot's known fields only; the AI summary of the overview leaves it out. The Console's Command page shows it as chips under the XAUUSD display (no new route; a hit rate with `no_scored_data` reads "no data yet", never 0 %). `xauusd_latest` keeps its six keys and now reads the newest flip warning or snapshot (`body.latest`: stance, confidence, candle, time). ## Source, CI and deploy (ADR-0012)

- **Linear history on main (owner-approved hardening (a), incident 2026-11-14, migration 0071).** The Forge merges a change request by fast-forwarding `main` to its head, so `main`'s current head must be on the head's **first-parent** chain. Update a branch by rebasing it onto `main`, or by a merge with `main` as the **first** parent (`git checkout -B <branch> origin/main && git merge <old head>`); never `git merge main` on the branch (that makes `main` the second parent). On 2026-11-14 such merges took `main`'s previous heads, the deployed versions, off `main`'s first-parent history, the deploy planner stopped planning and every deploy stuck. A head that contains `main` only through a second parent gets `history_blocked_reason = main_not_first_parent`: verdict `blocked`, never checked, never proposed for merge; the Forge's `changeState` checks it live and `forgeMerge` refuses the fast-forward too. The first-parent walk reads at most 500 commits (`FIRST_PARENT_WALK`, `workers/forge/src/merge.ts`); a longer branch is refused (fail closed). A head that does not contain `main` at all is still `not_based_on_main`.
